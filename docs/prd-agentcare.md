# PRD — AgentCare: Agentic AI for Patient Administration and Care Coordination

**Context**: 4-day hackathon build (solo), submission per `problem_statement_hackathon_details.md`. Every decision below was made and stress-tested in a grill-me session; scoring rubric and disqualification rules drove prioritization throughout.

## Problem Statement

Hospitals and clinics handle repetitive administrative work — registering patients, routing requests to the right department, checking doctor availability, booking and rescheduling appointments, collecting and organizing medical documents, sending reminders, and coordinating follow-ups — across fragmented forms, calls, and disconnected systems. Patients wait; staff drown in coordination overhead; nothing is auditable end to end.

The hackathon challenge: build **AgentCare**, an agentic AI application that understands an administrative patient request (e.g. *"I need a cardiology appointment next week. I also want to attach my previous ECG and blood reports."*), plans the required steps, invokes real tools, persists workflow state, and completes the task safely — while keeping all medical decisions under human supervision. It must never diagnose, prescribe, or replace a clinician.

## Solution

A multi-agent healthcare administration system with a **hub-and-spoke agent architecture**: a Coordinator agent plans which specialists a request needs; specialist agents (Department Routing, Appointment, Document, Follow-up) execute their lanes; a deterministic-first Safety guardrail layer wraps everything. The governing principle: **"the model proposes; the code disposes"** — LLMs draft intent, classifications, and wording; plain, unit-testable code owns every consequential decision (department validity, booking transactions, workflow state transitions, RBAC, safety verdicts, date resolution).

Patients interact chat-first through a Streamlit client; a FastAPI backend enforces authentication and role-based access, runs the agents, and persists everything — including a full execution trace of every LLM request/response, tool call, tool result, agent handoff, and state transition — to a SQL database. Staff review escalations, approve paused workflows, and can replay any workflow run step-by-step in a trace timeline.

The entire application runs end to end under any of three LLM providers selected by config: `groq`, `openai`, or `mock` — the mock being a deterministic "understudy" that replaces only the LLM brain while every tool, database write, and state transition stays real.

## User Stories

### Registration, identity, and access
1. As a patient, I want to register with my name, email, and password, so that I have an account to manage my hospital interactions.
2. As a patient, I want to log in and receive a session token, so that my subsequent requests are authenticated.
3. As a patient, I want to create and update my profile (date of birth, phone, preferred language, emergency contact), so that the hospital has my administrative details.
4. As a patient, I want to be rejected with a clear error when I try to access staff-only functions, so that role boundaries are real (enforced in the backend, not hidden buttons).
4a. As a patient, I want any attempt to read or mutate another patient's records with my own valid token (their appointment id, document id, reminder id, workflow run id) to be denied with 404 — not 403, which would confirm the record exists — and the denied attempt audit-logged, so that ownership is enforced on every id the API accepts, not just role.
5. As a staff user, I want to log in with a staff account and see staff-only views, so that I can perform administrative oversight.
6. As a system operator, I want every auth event (login, failed login, role-denied access) audit-logged, so that access history is reviewable.

### Submitting requests and the agent workflow
7. As a patient, I want to type a free-text administrative request in a chat interface, so that I don't have to navigate forms.
8. As a patient, I want the system to identify me from my session and load my context (profile, recent appointments, documents on file), so that returning patients don't re-explain themselves.
9. As a patient, I want the system to understand my administrative intent (book, reschedule, cancel, upload documents, ask status), so that the right workflow starts.
10. As a patient, I want my request routed to the correct department based on what I wrote, so that I don't need to know hospital structure.
11. As a patient, I want a workflow run created and its status visible for every request, so that I can see where things stand at any time.
12. As a patient, I want the conversation to remember earlier turns in the session (and survive an app restart), so that multi-turn requests work naturally.
13. As a patient whose request doesn't match any supported department, I want the request paused and sent to staff review rather than guessed at, so that I'm not misrouted.
13a. As a patient typing something outside hospital administration entirely (weather, jokes, homework), I want a polite template reply stating what AgentCare can help with — no workflow started, no tools fired, no staff escalation created — so that the system stays on-purpose and the escalation queue stays clean.
13b. As a staff user, I want off-topic turns recorded in the audit/trace trail but kept out of my review queues, so that oversight covers everything without drowning in noise.

### Appointments
14. As a patient, I want to see available doctors and slots for the routed department and my requested time frame, so that I can choose what fits.
15. As a patient, I want relative dates like "next week" resolved by code against today's real date, so that the booking lands when I meant it.
16. As a patient, I want the agent to present the exact doctor, date, and time and ask for my confirmation **before** booking, so that no appointment is committed on a silent guess.
17. As a patient, I want my confirmation read deterministically — a Confirm/Decline button click or an exact token ("yes"/"no"), with ambiguous replies re-asked rather than guessed — so that a booking can never commit on a probabilistic reading of my answer.
18. As a patient, I want the system to prevent double-booking me at overlapping times, so that conflicts are impossible.
19. As a patient, I want to reschedule an appointment (old slot released, new slot claimed atomically, with confirmation before commit), so that changing plans is safe.
20. As a patient, I want to cancel an appointment with an explicit confirmation of exactly which appointment is being cancelled, so that destructive actions are never ambiguous.
21. As a patient, I want my booking confirmation rendered from the persisted database record (not the model's memory), so that what I'm told is what is stored.
22. As a patient, I want to view all my appointments and their statuses, so that I have an overview without asking.

### Documents
23. As a patient, I want to upload a document and declare its type (ECG, blood report, prescription, referral, ID, other), so that my records are organized.
24. As a patient, I want the agent to verify that my document's content matches my declared type (via extracted PDF text + LLM) and flag mismatches for review, so that misfiled documents are caught.
25. As a patient, I want an exact duplicate upload (same content checksum) detected and rejected with an explanation, so that my file list stays clean.
26. As a patient, I want to see which required documents are still missing for my booked appointment (per-department rules), so that I arrive prepared.
27. As a patient, I want a follow-up task automatically created listing my missing documents, so that I'm reminded to supply them.
28. As a patient, I want to view all my uploaded documents with their types and statuses, so that I know what's on file.
29. As a staff user, I want document type mismatches surfaced for review, so that misdeclared files get human eyes.

### Reminders, follow-up, and notifications
30. As a patient, I want an appointment reminder scheduled automatically when I book, so that I don't miss visits.
31. As a patient, I want reminders to actually fire at their scheduled time via a background scheduler and appear in my in-app notifications, so that reminding is real, not decorative.
32. As a patient, I want a post-visit follow-up task created for follow-up-type appointments — triggered by the visit-completion sweep marking my past appointment completed — so that continuity of care is coordinated by the running system, not by hand-edited data.
32a. As a staff user, I want to flip a swept appointment from completed to missed (typed action), so that no-shows are recorded and missed-visit follow-up can happen.
33. As a patient, I want to view my pending reminders and follow-up tasks, so that I can see what's coming.
34. As a system operator, I want the simulated delivery channel (log-based NotificationService) to record every send, so that delivery is verifiable without real SMS/email infrastructure.

### Safety and escalation
35. As a patient describing an emergency (e.g. chest pain), I want the deterministic keyword screen to catch it immediately — before any LLM runs — block normal processing, create an escalation, and tell me to seek urgent care, so that emergencies are never handled by a booking bot.
36. As a patient asking for a diagnosis, prescription, or dosage, I want the system to refuse (hybrid rules + LLM classification), explain it handles administration only, and escalate when appropriate, so that the clinical safety boundary holds.
37. As a patient, I want routing language to stay administrative ("routing you to Cardiology", never "sounds like a heart condition"), so that the system never implies a diagnosis.
38. As a staff user, I want every escalation persisted with reason, status, and reviewer, so that human review is a recorded workflow, not a dropped ball.
39. As a staff user, I want to approve, reject, or redirect a paused workflow (low-confidence routing, unsupported department), and have the workflow resume from my decision, so that humans stay in the loop on uncertainty.
40. As a system operator, I want prompt-injection attempts ("ignore previous instructions...") to fail against code-enforced guards and be recorded, so that the safety layer is adversarially robust.

### Staff operations
41. As a staff user, I want a queue of patient requests and their workflow states, so that I can monitor operations.
42. As a staff user, I want an escalation/approval queue with one-click decisions, so that reviews are fast.
43. As a staff user, I want to toggle departments and doctors active/inactive and add slots for a doctor, so that I can manage capacity (creation of departments/doctors comes from the seed script).
44. As a staff user, I want to view the full audit history (who did what, to which entity, when), so that every action is accountable.
45. As a staff user, I want a per-workflow-run **trace timeline** — every LLM request, LLM response (including reasoning and proposed tool calls), tool call with arguments, tool result with duration, agent handoff, and state transition, in order, color-coded by agent — so that any run is fully auditable and debuggable.

### Provider switching and operations
46. As an operator, I want to switch the entire application between `mock`, `groq`, and `openai` by changing one config variable, so that the same system runs with or without API keys.
47. As an operator running mock mode, I want every workflow (booking, reschedule, cancel, documents, escalation, confirmation) to execute genuinely — real tools, real DB rows, real traces — with replies templated from persisted tool results, so that mock mode is a real mode, never canned output.
48. As an operator, I want per-provider model configuration (separate model vars per provider, never one shared variable), so that switching providers can't send one provider's model name to another.
49. As an operator, I want sensitive fields (phone, email, DOB, IDs) always redacted in logs and traces with no override, and free-text content gated by a config switch, so that PII handling is enforced at write time.
50. As an operator, I want optional Phoenix tracing enabled by a flag with zero behavior change when off, so that deep dev-time observability costs nothing in production.
51. As a judge/evaluator, I want to clone the repo, follow the README, seed synthetic data, and run everything locally on SQLite with no external services, so that evaluation is frictionless.

## Implementation Decisions

### Stack
- **Backend**: Python + FastAPI — owns JWT auth, RBAC, agent orchestration, tools, persistence. **Frontend**: Streamlit as a thin client calling the API with the user's token (chat via `st.chat_*`, uploads via `st.file_uploader`, separate patient/staff views). All frontend API calls go through a single shared `api_client` module.
- **Agent framework**: Google ADK, with a **LangGraph fallback** decision gate at end of day 1. To keep the swap cheap: tools are plain Python functions, prompts live in their own module, and ADK is confined behind a single orchestrator entry point (`run_workflow(user, message, session_id)`).
- **LLM providers**: one `LLMProvider` interface, three implementations — `groq`, `openai`, `mock` — selected by `LLM_PROVIDER`. Per-provider model env vars (e.g. separate Groq/OpenAI model settings); never a single shared model variable. `.env.example` defaults to a real provider.
- **Database**: SQLAlchemy + `DATABASE_URL`. SQLite file by default (never in-memory); Supabase Postgres for the optional deployed instance via connection string only — no Supabase SDK, auth, or storage. Build note: FastAPI handlers and the APScheduler poll job share the one SQLite file — enable WAL mode at engine creation (SQLite-only pragma, no-op under Postgres) or concurrent writers meet "database is locked".
- **Config**: environment-based throughout; `.env` gitignored from the first commit; committed `.env.example` documents every variable.

### Agent architecture (highest-weighted scoring area)
- **Five agents**, each with its own prompt and toolset: Coordinator, Department Routing, Appointment, Document, Follow-up. **Safety is a guardrail layer** (callbacks + escalation tool), not a sixth agent.
- **Per-agent context contract**: the Coordinator receives the (windowed) transcript **while a run is live**, where its job is to classify a message against what came before; on a **fresh turn** it receives the current turn and the patient's own record only, because planning is a question about *this* message and the transcript demonstrably cost more than it gave (a planner reasoning over a session in which "conflicting" had been a valid answer submitted that word as a plan step five times running, and the request never started). Specialists receive **no transcript at all** — only the typed task and the state they need (department, resolved dates, patient id). Where language is the specialist's job, the current request text rides inside the typed task (Routing classifies the patient's words, so its task includes them) — it's the *history* specialists never see. One patient message costs full context once, not once per agent.
- **Topology: hub-and-spoke.** Specialists never talk peer-to-peer; all interaction is Coordinator delegation + shared persisted state (ADK session state, WorkflowRun row, TraceEvent rows). Cross-agent data flow is real: Routing's department feeds Appointment's slot search and Document's required-docs rules; Appointment's appointment id and Document's missing-docs list jointly drive Follow-up's output.
- **Sequencing: LLM plans, code enforces — and the plan is a typed artifact.** The Coordinator LLM decides *which* specialists a request needs (a doc-only upload skips routing/booking), but it emits the plan as a schema-validated list of steps drawn from a closed enum (route, book, documents, follow_up) — never freeform prose. Code enforces dependency order on the parsed plan (no booking before routing; no doc-diff before department known); a plan that fails schema validation is a malformed-output error handled by the retry ladder, not executed. Rationale: code can't enforce ordering on a plan it can't parse — freeform delegation is a slip written in prose.
- **Multi-intent messages take the superset plan.** A single message can carry two intents ("I need a cardiology appointment next week. I also want to attach my previous ECG") — the canonical hackathon request is exactly this shape. Intent detection must never pick whichever intent matches first: a message containing a booking intent takes the booking plan (route, book, documents, follow_up), which already contains the document steps — the narrower intent rides inside the wider plan, never the reverse. Pinned because the failure mode is silent: a documents-only plan happily "succeeds" while the appointment the patient asked for never happens. Layer-1 scenario: the canonical two-intent message must produce a plan containing route AND book.
- **Decision bins** (the architectural spine, recorded as an explicit table in the architecture docs): probabilistic — reply wording, intent/entity extraction, classification proposals; deterministic — department validity against the Department table, slot/conflict transactions, workflow state machine transitions, RBAC, first-layer safety screen, checksum dedup, required-docs diff, date resolution.
- **No A2A protocol** — agents are in-process; a README paragraph notes where A2A/MCP would apply in a service-split deployment. An MCP tool server wrapper is a day-4 optional tie-breaker, strictly behind deploy + video.

### Safety, approvals, and the confirmation flow
- **Hybrid safety detection**: deterministic keyword/pattern screen runs first and always (emergencies, diagnosis/prescription-seeking) — it works even if the LLM misbehaves — followed by an LLM classification pass for subtle cases. Both paths persist Escalation + AuditEvent records.
- **Escalation dedup (one open escalation per run)**: the safety screen fires on every message, but record creation is deduped — if the run already has an open Escalation, subsequent triggers **attach** to it (occurrence count + latest message appended to its metadata, audit event per trigger) rather than creating new rows. A frightened patient typing "chest pain" five times produces one queue item with five recorded triggers — the staff queue stays as clean of panic-repeats as it is of off-topic noise, and repetition is visible as urgency context on the single record, not scattered across five.
- **Two staff-approval triggers**: (1) emergency/diagnosis flags → block + escalate; (2) low-confidence or unsupported routing → workflow pauses in a pending-review state; staff approve/reject/redirect; workflow resumes.
- **The staff decision path is LLM-free.** A staff approve/reject/redirect is a typed action code applies directly to the workflow — no model reads, interprets, or rephrases it. Human decisions enter the system as validated structured input, same as any other consequential state change.
- **Scope gate (on/off-topic guardrail)**: the Coordinator's intent detection classifies three ways — supported administrative intent (workflow proceeds), unsafe (safety path), off-topic (polite deterministic template reply listing what AgentCare handles; no workflow spawned, no tools fired, no escalation created — off-topic is noise, not a human-review case). Model proposes the class; code disposes: only supported intents can spawn workflows, and the refusal is a template, not LLM freeform (identical in mock and live modes; the mock's unrecognized-input fallback IS the scope message). Ordering: safety screen first (a message can be off-topic-shaped and an emergency), then scope gate, then routing. Off-topic turns still get audit/trace rows.
- **Confirm-before-commit** for book, reschedule, and cancel: the Appointment agent presents doctor/date/time from real slot data, the workflow enters a pending-confirmation state, and only the patient's confirmation triggers the mutating tool. Reuses the same pause/resume machinery as staff approvals. Rationale: schemas catch malformed arguments; only confirmation catches well-formed fabrications — an LLM given "next week" with no other anchor can silently resolve it differently across runs while remaining schema-valid and plausible (ambiguous dates, wrong slot pick, wrong appointment on cancel).
- **Every commit-time failure exits the same way: clear the proposal, return to selection, offer alternatives.** When the re-check inside the commit transaction fails (slot taken, double-booking) — for book, reschedule, AND cancel alike — code clears `pendingProposal`, transitions back to slot selection, and the reply carries fresh alternatives. A failure path may never leave a stale proposal confirmable again: a proposal pointing at a dead slot plus a patient clicking Confirm is a loop with no exit (the boundedness invariant applies to failure paths too). Layer-1 scenario per action type: sabotage the proposed slot between proposal and confirm → expect proposal cleared, alternatives offered, and a second Confirm click no-ops.
- **The pending proposal is typed state.** What the patient is confirming (action, slot id / appointment id) is persisted on the WorkflowRun row at proposal time; the yes/no is resolved against that row, never against the transcript — so confirm-before-commit survives history windowing, session expiry, and restarts. (The same rule that keeps withdrawal out of prose keeps the proposal out of it too.)
- **The confirmation answer is read deterministically — commitment requires a click or an exact token; the model may decline or re-ask, but it can never confirm.** Reading order: (a) ✅ Confirm / ❌ Decline buttons render **with the first proposal** (not as a stall fallback) — a click arrives as a typed action, zero interpretation; (b) typed text goes through an exact-token match in code first (yes / confirm / book it → confirm; no / cancel → decline); (c) only text the tokens can't read reaches the model, whose **only allowed verdicts are decline or non-answer** — an ambiguous reply ("no wait — yes, the Tuesday one") can decline or trigger a re-ask, never commit. Cost-asymmetry: a wrongly re-asked "yes" costs one tap; a wrongly committed "no" books an appointment against the patient's word at the exact step built to prevent that. This closes the loop: proposal typed, answer typed, commit coded.
- **Confirmation-stall containment**: side questions and non-answers in pending_confirmation are legal self-stays, but the re-ask loop is bounded — a non-answer counter on the run; after N non-answers (default 3), re-asks switch from LLM-worded to a **code-templated explicit framing** ("press Confirm or reply 'yes'"), costing zero further LLM turns and behaving identically in mock and live. (Buttons are present from the first proposal — the stall bound caps the *wording* spend, not button availability.) A stall never resolves implicitly in either direction: no auto-commit, no auto-decline — the run stays in pending_confirmation until an explicit answer, a withdrawal, or a supersede.
- **Date fabrication defense**: today's date injected into every agent prompt; relative dates ("next week") resolved in code via a `resolve_date` tool shared by mock and live modes.

### Documents
- Patient declares type at upload; the Document agent verifies content matches (pypdf text extraction + LLM) and flags mismatches. Images are classified by declared type only (no OCR).
- Duplicate detection: SHA-256 checksum per patient; exact match rejected with audit event. **Known limit, stated in the README**: exact-checksum only — a re-exported ECG with different bytes (new export, scan, or compression) passes as a distinct document. Accepted scope; content-level similarity detection is out of scope.
- Missing documents: per-department required-document rules table, diffed against uploads after booking; missing items become a follow-up task. **Task dedup (one open missing-docs task per appointment)**: the diff is an upsert, not an insert — re-running it (after a later upload, or any document workflow touching the same appointment) updates the existing open task's item list, closes the task when the list empties, and never spawns a sibling. Each pass writes an audit event; the task row count never grows past one per appointment.
- Files stored on local disk; metadata + checksum in the database.

### Appointments
- Seeded doctors with pre-generated slot rows; booking checks slot availability and patient double-booking inside a transaction; statuses flow pending → confirmed → completed/cancelled; reschedule releases the old slot and claims the new one atomically; confirmations are always rendered from persisted rows.
- **Cancel/reschedule cascades to derived rows in the same transaction.** Reminders are keyed to the appointment; the transaction that releases the slot also updates them: cancel → linked reminders marked cancelled; reschedule → reminder rescheduled for the new time (update or cancel-and-recreate). Without this, the reminder channel — pure code — delivers a fact frozen at booking time ("your Friday appointment is tomorrow") after the appointment moved: the exact stale-fact bug the receipt discipline kills for model output, reintroduced by a code path. The rule generalizes as the **derivation invariant**, sibling of the boundedness invariant: every row automation derives from another row needs an update rule for when the source changes, applied in the source's transaction.

### Consequential reply wording (LLM-composed, eval-guarded, pinned fallback)
- Replies that state facts (booking confirmation, reschedule/cancel identity, safety refusal) remain LLM-worded in live mode, grounded on tool results — accepting that reply prose is the one untyped model output (schemas validate slips in; nothing validates sentences out, so a model can misstate a date while sounding certain). Guards:
  1. All confirmation-bearing replies are built from a single `render_confirmation(entity_id)` seam that **re-reads the persisted row** — never from conversation history.
  2. Layer 2 live evals grade the **fact fields** of these replies exactly against the DB row (doctor name, weekday + date, time, reference id; cancel/reschedule evals assert the *correct appointment* is named), unlike other wording which is graded tolerantly. Fact-drift cases run N=5 with a **100% pass bar** — one miss is a failure.
  3. **Fallback trigger**: any fact-drift failure flips `render_confirmation` to code-templated output (code sends the string rendered from the re-read row; the model writes nothing that turn — mock and live share the path). The seam exists from day 1 so the swap is a one-function change, not a refactor.

### Workflow state machine (pinned before build day 1)
- `WorkflowRun.status` is the deterministic machine everything hangs off (pause/resume, escalation resume, confirm-before-commit). **Initial states (two)**: runs are created directly in `in_progress` on intent acceptance (after the safety screen and scope gate pass — off-topic input never spawns a run), or directly in `escalated` when the safety screen fires on a session's opening message — the one case where the highest-priority path would otherwise have no run to key the Escalation to. This door opens only for safety: every Escalation stays keyed to a real workflow_run_id (no nullable FK, no orphan special-case in trace queries), and an emergency-first-message replays in the trace timeline like any other run. States and legal transitions — any *state change* not in this table raises and is audited as an illegal-transition attempt; a message that triggers no transition is legal (state unchanged — e.g. a side-question while in pending_confirmation gets answered-and-stay or a re-ask; the table governs changes only):

| From | To | Trigger |
|---|---|---|
| (created) | in_progress | intent accepted (safety screen + scope gate passed) |
| (created) | escalated ⊗ | safety screen fires on the opening message of a session (no prior run exists) |
| in_progress | pending_confirmation | Appointment agent proposes book / reschedule / cancel |
| pending_confirmation | in_progress | patient confirms (commit + continue plan) or declines (back to slot selection) |
| in_progress | pending_review | low-confidence or unsupported routing |
| pending_review | in_progress | staff approve or redirect (typed action) |
| pending_review | rejected ⊗ | staff reject (typed action) |
| in_progress | cancelled ⊗ | patient withdraws the request ("never mind, forget it" — model proposes withdrawal, code applies) |
| pending_confirmation | cancelled ⊗ | patient withdraws instead of confirming/declining |
| pending_review | cancelled ⊗ | patient withdraws while awaiting staff review (reason=withdrawn_during_review) |
| any non-terminal | escalated ⊗ | safety verdict: emergency / diagnosis-seeking (screen runs on every incoming message, whatever the current state) |
| in_progress | completed ⊗ | all plan steps done |
| in_progress | failed ⊗ | unrecoverable error after bounded retries |

  (⊗ = terminal for automation. `escalated` hands ownership to the Escalation record, whose lifecycle is named per path: review-type escalations open → approved / rejected; safety/emergency escalations open → acknowledged → resolved — staff UI language must never imply "approving" an emergency.)
- **Withdrawal is typed state, never chat prose.** A withdrawal that lived only in conversation history would leave the state row misrepresenting reality (a `pending_review` row reading "waiting to resume" for a request the patient abandoned) and would guarantee the zombie approval: staff act on a dead request because the one changed precondition was never persisted. Hence `cancelled` is reachable from every patient-facing non-terminal state. The staff queue keeps visibility via a query, not a live state: active reviews on top, a collapsed "withdrawn while pending" section below — views read terminal states; the machine never keeps a run alive to power a UI.
- **The one state withdrawal must NOT close: `escalated`.** A chest-pain escalation followed by "actually forget it" stays in front of humans — already guaranteed, because `escalated` is terminal for automation and only staff can close the owning Escalation record.
- **Withdrawal misclassification cost-asymmetry** (why the edge is safe to take): wrongly cancelling on "never mind about the ECG" costs a one-sentence recovery (patient re-asks, new run); the missing edge costs staff time on dead requests plus patient-facing zombie actions. Bias toward the shrug.
- **One active run per patient, with a message→run mapping rule.** When a message arrives while the patient has a non-terminal run, it is classified into one of five classes — model proposes the class, code applies the consequence:

| Class | Example (during a pending cardiology booking) | Consequence |
|---|---|---|
| continuation | "yes", "Tuesday" | feed the waiting run (confirmation answer, slot choice) |
| complementary | "also, here's my old ECG" + upload | **code appends a step from the plan enum** (e.g. documents) to the active run's plan — never supersede; the booking survives. A deterministic append, not an LLM re-plan — does not consume the re-plan budget |
| conflicting | "actually make it dermatology", or a rephrase of the same goal ("book me a cardiology appointment" while run #1 sits in review) | supersede: old run → cancelled (reason=superseded, audit event), new run proceeds, reply notes the earlier request was closed |
| side question | "what docs do I have on file?" | answer-and-stay (read-only; never spawns a run, never supersedes) |
| off-topic | "what's the weather like?" (while a run is active) | template scope reply, self-stay: no transition, no supersede, and the run's stored request text is never touched |

  Code validates the proposed class before applying it: a message carrying the same intent type as the active run (a second booking request) can never be complementary — it is conflicting by definition; complementary is reserved for compatible intent types (document upload, reminder preference) that serve the active goal. Supersede remains the answer to the rephrase-zombie problem — it is now the consequence of exactly one class instead of the default for everything. Cost-asymmetry: a wrongly superseded review costs a re-ask, a zombie resume costs an incident — but a wrongly superseded *cooperation* (the ECG-during-confirmation trace) costs a lost booking, which is why classification precedes consequence.

  **The scope gate runs inside the mapping too, not only at run creation.** The safety screen already fires on every message regardless of state, and off-topic needs the same treatment — otherwise an off-topic message defaults to "continuation" and gets appended to the run's request text, contaminating what routing and appointment matching read later. Classification order within a turn: withdrawal → off-topic → side question → complementary → conflicting → continuation. Layer-1 scenario: off-topic during an `in_progress` lull → template reply, run state and request text byte-identical before and after.
- **A resume is a fresh proposal, not a replay.** On any resume (staff approval from pending_review, patient confirmation from pending_confirmation), code re-validates preconditions against **current** DB state before acting: does the patient already have an upcoming appointment in this department? is the slot still free? is the run still the patient's latest? A failed precondition never acts silently — it returns to the patient as a question (or to staff with the changed context). The slot re-check inside the commit transaction is one instance of this general rule.
- Every transition writes an AuditEvent and a TraceEvent; the transition table is unit-tested exhaustively (each legal edge succeeds, a sample of illegal edges raises).
- **Every transition is a compare-and-swap.** Transitions execute as a conditional update — set the new status only where the row still holds the expected old status; zero affected rows means another request got there first, and the loser treats it as a no-op (re-read state, respond accordingly), never a crash or a double-fire. Motivating trace: a double-clicked confirm button sends two requests that both read pending_confirmation — the booking transaction would catch the double-book, but the CAS stops the race one layer earlier and applies uniformly to every edge, not just booking. One pattern everywhere transitions happen; SQLite's write serialization plus WAL makes it cheap. Unit test: two sequential transition attempts from the same expected state — first succeeds, second no-ops.
- **Staff-caused terminal transitions write a notification row.** A patient whose run is rejected (or otherwise closed by staff while they're not looking) learns via the in-app notification panel — the channel already exists; terminal transitions triggered by staff typed actions deliver through it. Patient-caused terminals (cancelled by withdrawal, supersede) are acknowledged in the reply itself.
- **Staff-caused resumes are lazy-continue: a staff approval changes state and notifies; the run advances only on the patient's next interaction — humans resume conversations, state changes don't.** Approval flips pending_review → in_progress and writes a notification ("approved and routed to Cardiology — open the chat to continue"), then stops. No agent executes, no outbound chat turn is written into an empty room, no non-answer clock starts against a patient who doesn't know a question exists. The patient's return is the inbound that wakes the run. This composes with two pinned rules rather than fighting them: "a resume is a fresh proposal" — under lazy-continue the slot search runs while the patient is present, so the data is current by construction; and the trace bracketing rule — every outbound still follows an inbound, with no special case for system-initiated turns.
- Companion entity statuses, for completeness: Appointment pending → confirmed → completed | missed | cancelled. Every appointment transition has a named actor: pending → confirmed (patient confirmation), confirmed → cancelled (patient/agent action), **confirmed → completed (the poll job's visit-completion sweep — time-triggered, no human actor exists)**, completed ↔ missed (staff typed action correcting the sweep). AppointmentSlot available ↔ booked (released on cancel/reschedule). No slot hold during pending_confirmation — the booking tool re-checks availability inside the commit transaction; if the slot was taken meanwhile, the patient returns to slot selection.

### Reminders and follow-up
- Reminder rows with scheduled times. **Delivery mechanism: a single periodic APScheduler job polls the Reminder table for due rows** (due = scheduled time ≤ now and status pending), marks them sent, and delivers via the in-app notifications panel plus a log-writing NotificationService (simulated SMS/email).
- **The poll job also owns time-triggered state transitions (the visit-completion sweep).** A second query in the same tick finds confirmed appointments whose end time is past and marks them completed (audit event per transition) — which is the real trigger for post-visit follow-up task creation. Staff can flip a swept appointment to **missed** instead (typed action; missed appointments satisfy the "detects missed or incomplete workflows" duty of the Follow-up agent). Rationale: pending → confirmed has a patient pressing buttons; "the visit is now over" has no actor — any transition triggered by the passage of time rather than a message or click needs a process that watches the clock, and the poller is that process. The sweep reads time through the clock seam, so tests drive it with a frozen date: seed a past-dated confirmed appointment, run one tick, assert completed + post-visit task exists. Deliberately not per-reminder in-memory jobs: DB polling is restart-safe (reminders created before a crash still fire after restart — the table is the source of truth, not scheduler memory) and deterministic to test (seed a due row, run one poll tick, assert delivery).
- **Poisoned-row protection** (restart-safety cuts both ways — a row whose delivery throws would otherwise be retried every tick forever, and could block the batch): (1) per-row try/except — one failing row never aborts the rest of the batch; (2) an attempt counter incremented *before* each delivery attempt — after N failures (default 3) the row transitions to status=failed with an audit event and is never polled again; (3) ordering pinned as **deliver-then-mark with dedup**: the in-app notification insert is idempotent (keyed by reminder id), so a crash between delivering and marking sent causes a bounded re-attempt that dedup makes invisible — never unbounded re-delivery. Test: a poisoned-row fixture must reach failed at exactly N ticks while its batchmates deliver normally. Post-visit follow-up tasks for follow-up appointments; missing-document tasks from the Document agent.

### Memory
- **Tier 1**: ADK DatabaseSessionService — conversation history and session state persisted in SQL (also satisfies the mandatory persistent-agent-state requirement).
- **History windowing (the boundedness invariant applied to Tier 1)**: history is an automated writer hiding behind the framework — appended every turn, never trimmed, and sent whole to the LLM, so prompts grow monotonically toward context/rate limits. Rule: **persist everything (audit needs it), send the model only the last N turns (default 15, config) plus the patient-context tool result.** Safe in this design specifically because facts are never read from history — receipts re-read rows, status questions call tools — so windowing costs the model old chit-chat, never truth. Same window in mock and live.
- **Session lifecycle: sessions are cheap and disposable** — a new session per conversation is fine, because continuity is Tier 2's job, not Tier 1's. The Coordinator's first tool call loads profile, appointments, and documents from the DB; a returning patient re-explains nothing even with a fresh, empty history. Continuity lives in the database; sessions may be short-lived without losing it.
- **Authority ranking (session state vs rows)**: the DB row is authoritative for every consequential fact; session state is the model's scratchpad (conversational hints, preferences). **No tool or transition may read a consequential value — pending slot, resolved department, run status — from session state when a row exists.** "History is for understanding, the database is for statements," applied to the other memory store; a crash between writes can desynchronize the two, and this rule decides who wins.
- **Tier 2**: the SQL database is the long-term memory — the Coordinator's first tool call loads patient context (profile, recent appointments, documents on file); lightweight preferences ride in user-scoped session state.
- **No vector/semantic memory** — unscored, extra infrastructure, and embeddings would break mock-mode end-to-end parity.
- **PII posture for history (state in README)**: raw chat history necessarily contains whatever the patient types — it is the model's working memory and cannot be redacted without lobotomizing it. The redaction guarantee covers traces and logs; history is stored raw **by design**, protected by access control (ownership-checked endpoints) rather than redaction — a decision, not an oversight.

### Observability and auditability (user-hardened requirement)
- **TraceEvent table in the application database is the system of record** — written via ADK callbacks and service-layer hooks at **nine capture points**:
  1. **Inbound event** — opens every turn, captured independently of any LLM call (an emergency caught pre-LLM, a mock/template path — the triggering input is in the trace regardless). **An inbound event is a chat message OR a typed action**, distinguished by an author field (`patient-message | patient-action | staff-action`) — a confirm-button click and a staff approve are inbound events, not exceptions to the grammar. The system has two front doors; the grammar recognizes both.
  2. **Guard verdict** — the safety screen and scope gate log their verdict on **every** message, including passes, with the rule that matched or didn't. A guard that only logs when it fires is half an instrument; the false-negative hunt ("why didn't it fire?") needs the passes.
  3. LLM request (full messages sent).
  4. LLM response (text incl. reasoning, proposed tool calls, token counts) — **or LLM error**: every request event gets exactly one terminal partner, response or error (timeout, rate limit). A request with no terminal event then means exactly one thing — crash mid-call — making hung turns diagnosable from the table alone.
  5. **Validation verdict** — every schema/class validation (Coordinator plan, tool arguments, message→run class) writes accepted/rejected + reason + attempt number. Without it, a rejected plan followed by a retry reads as the model inexplicably calling twice; the rejection is the debugging payload.
  6. Tool call (name + arguments as emitted).
  7. Tool result (value, duration, success/error).
  8. Agent handoff.
  9. **Outbound reply, with an `author` field (`llm | template | guard`)** — written for every reply regardless of who wrote it. Code-authored turns (scope-gate template, templated-receipt fallback, safety block message) are the system's most deterministic moments and must not vanish from the timeline.

  Rows keyed by workflow run id + session id + sequence; one query replays any run in order. **Bracketing rule**: every turn is bracketed — one inbound event (either kind), one outbound event, whatever happened in between; for staff-action turns, the notification row counts as the outbound. General lesson, pinned: when a new kind of input is added, every validator that enumerates input kinds is now wrong — update the checker in the same commit that adds the door.
- **Born-once storage**: each message is stored once, at the event where it originated. LLM-request rows store only the *new* content of that call plus a window descriptor (message range + system prompt version) — never a re-copy of history. Replay reconstructs any request by join; history rows are immutable; system prompts are versioned so the descriptor stays resolvable.
- **Built-in ADK tracing vs TraceEvent — the decision in writing**: ADK's OTel tracing is the optional dev microscope (it's what Phoenix consumes), env-gated, off by default. ADK *callbacks* write TraceEvent, the system of record, in our database. A **day-0 spike verifies the callbacks cover all nine capture points** — a coverage failure there is LangGraph-gate evidence, not something to discover on day 2.
- **Trace/audit split for the scheduler**: the poll job acts with no run and no session — its consequential writes (reminder deliveries, visit-completion sweeps) live in AuditEvents, not TraceEvents. Stated rule: agent activity → trace; scheduler activity → audit. The timeline doesn't "miss" reminder sends — they're in the other ledger by design.
- **Staff UI trace timeline**: per-run chronological, expandable, color-coded by agent.
- **Two-tier write-time redaction**: sensitive keys (phone, email, DOB, IDs) always redacted, no override, proven by a unit test; free-text content stored by default (synthetic data) behind a content-inclusion config switch documenting the production posture.
- **Correlation**: workflow run id propagated through logs, AuditEvents, and traces. **TraceEvent's run id is nullable — for off-topic turns only**: off-topic input deliberately spawns no run but still gets trace/audit rows, so those rows carry a session id and a null run id. (Escalations never need this — the run-born-escalated rule keeps every Escalation keyed to a real run.) Consequence for queries: "everything in this session" keys on session id; "everything in this run" keys on run id; the trace viewer uses the right one per view.
- **Arize Phoenix**: optional, env-gated, self-hosted, auto-instrumenting ADK (LangChain instrumentor under fallback); a dev-time bonus, never a dependency.
- **AuditEvent** records every tool call, auth event, and approval action — the business-level trail alongside the execution-level trace.

### Mock provider (replaces the brain, never the hands)
- Implements the same provider interface as real providers (duck-typed at the ADK model seam); inspects the message list to either propose a deterministic tool call (rule-based intent/entity extraction incl. `resolve_date`) or compose a reply **templated from live tool results** — never canned text (hackathon rule: no hardcoded final responses). Every workflow path must have a mock-mode route; new agent behavior ships with its mock equivalent or mock coverage silently rots.
- Tests and eval runners force the mock provider in code before imports (env loading is setdefault; shell beats `.env`).
- README states honestly what mock proves (plumbing: routing, schemas, state, RBAC, redaction, traces) and what it cannot (language understanding).

### Failure policy (per stage)
- LLM call: bounded retries → graceful message → workflow state preserved. Tool call: retry → error state persisted → escalation if unrecoverable. Conversation-level: escalation to staff is the designed error handler, not a crash. This table doubles as the mandatory error-handling/recovery requirement.
- **Rate limits are a distinct failure class, not an error.** A 429 honors retry-after and backs off **without consuming a bounded-retry slot** — retry budgets exist for broken calls, not throttled ones. Corollary for the eval suite: the Layer-2 runner paces its cases — N=5 runs × multiple agent calls per turn is a burst profile that will trip Groq's tokens-per-minute limit if fired back-to-back.
- **Iteration budget (the successful-calls loop cap).** Error retries are bounded above, but a loop of *successful* calls never trips a retry ladder (e.g. slot search returns empty → agent widens the range → empty → widens again, every call succeeding, forever). Explicit caps, config-driven, not reliant on any implicit framework limit: **max tool iterations per agent turn** (default 8) and **max one re-plan per run** for the Coordinator. Exceeding either transitions the run to `failed` with a graceful message to the patient ("I couldn't complete this — a staff member can help"), plus audit + trace rows recording the budget exhaustion. One config value each, unit-tested (a stub tool that always returns empty must produce `failed` at exactly the cap, never an unbounded loop).

### Seed data (defaults)

All data obviously fake.

Rule: seed scripts use ranges that always contain slots ("next week"), and a **seed self-check** asserts after seeding that no seeded patient holds a non-terminal run and every scripted flow reached its intended terminal state. A judge can clone and demo on any day of the week.

## Testing Decisions

**Philosophy**: test external behavior through the six public seams, never internals. High coverage (~80%) on backend logic, written alongside each component (test-as-you-go, not a final test day). Streamlit rendering code excluded from coverage targets, but frontend↔backend wiring is explicitly in scope (user requirement).

Four verification layers, cheapest and most deterministic first:

1. **Golden set** (user-required) — JSON golden files per retrieval surface: department resolution (incl. synonyms and the unsupported case), slot availability (exact slot ids incl. exclusions), patient context, required-docs diff, duplicate checksum verdicts, reminders due (incl. the cascade case: book → reschedule → list due reminders at the old reminder time — old row absent, new row present), and natural-language→query-arguments (relative dates → exact resolved ranges). Runner seeds a fresh DB, freezes the clock, calls the **real tool functions** (not raw SQL), diffs against golden JSON; an update flag re-blesses intentional changes via reviewable git diff. No LLM involved; runs in CI; never flaky.
2. **Unit/coverage tests** — RBAC enforcement at both levels: role (patient token vs staff endpoints and service-layer re-checks) and **ownership (the cross-patient probe: patient A's valid token + patient B's appointment/document/reminder/run id → 404 on every id-taking endpoint, denied attempt audited — the one-digit-edit judges try first)**, booking conflicts and atomic reschedule, **exhaustive state-machine transition tests against the pinned transition table** (every legal edge succeeds; a sample of illegal edges raises and audits), Coordinator plan schema validation (malformed/out-of-enum plans rejected into the retry ladder, never executed), checksum dedup, redaction (a test proves sensitive keys are actually redacted — "an alarm you've never tripped is a decoration"), restart-survival of persisted data.
3. **Scenario evals, Layer 1 (mock-forced, CI)** — one JSON scenario per pinned behavior (booking happy path, ambiguous dates, reschedule/cancel, doc mismatch, missing docs, emergency escalation, diagnosis-seeking paraphrases, prompt injection, SQL-in-field, RBAC probes, off-topic input → template reply with zero tools fired and no escalation, mixed off-topic + emergency → safety wins, emergency as the session's very first message → run born in escalated with a real run id and full trace, ambiguous confirmation reply ("no wait — yes, the Tuesday one") → re-ask, never a commit, withdrawal: "never mind" mid-booking → run cancelled with correct reason, no booking tool fired, decline: "no" at confirmation → no mutating tool fired, slot still available, run back in slot selection, stall: three non-answers → run still pending_confirmation, reply author flips to template, zero LLM calls after the switch, supersede: conflicting rephrase while run paused → old run cancelled with reason=superseded + notice in reply, complementary: doc upload during pending_confirmation → documents step appended and the booking survives, stale resume: staff approve a superseded/outdated run → precondition re-validation blocks silent action, lazy-continue: staff approve while patient offline → status flips + notification row, zero outbound chat turns until the patient's next message, canonical two-intent message → plan contains route AND book, superset never narrowed, seed self-check → no seeded patient holds a non-terminal run on any boot day, slot sabotage at commit (book/reschedule) → proposal cleared + alternatives, second confirm no-ops, off-topic mid-run → template reply, request text untouched) with expect keys: tools fired (exact, ordered), tool **arguments** (resolved dates), department, workflow status, escalation created, and forbid-lists (diagnosis language, prompt-leak canaries, other patients' data). Framework-agnostic pytest runner (not ADK's eval tooling — must survive the LangGraph fallback). Mock forced via env set before imports.
4. **Scenario evals, Layer 2 (live)** — same JSON scenarios against Groq, pytest-marked and skipped in CI, run manually before demo/submission; plumbing keys graded exactly, wording tolerantly — **except fact fields in confirmation-bearing replies** (doctor name, weekday + date, time, reference id, and which appointment a cancel/reschedule names), which are graded exactly against the DB row; fact-drift cases run N=5 with a 100% pass bar, and any miss triggers the pinned fallback (code-templated `render_confirmation`). Safety-critical cases run N=5 with a pass-rate threshold.

**Wiring tests** (user requirement): the shared `api_client` exercised against the real FastAPI app via httpx TestClient — every endpoint the UI touches, with real tokens for both roles; plus headless Streamlit AppTest tests (log in, submit request, assert rendered data came from the API). Mock mode emits identically-shaped traces, and wiring tests assert on TraceEvent rows — proving "everything is captured" rather than claiming it. **Trace well-formedness checker**: for every Layer-1 scenario, assert the trace parses against the turn grammar — inbound (message or typed action) → guard verdict → [request → (response|error) → validation → tool call → tool result]* → (transition) → outbound (reply or, for staff actions, notification row) — with no unpaired requests and no unbracketed turns. Typed-action turns (confirm click, staff approve) follow the same bracket rule — the checker must pass the system's most deterministic flows, not just its chattiest. One checker converts trace completeness from a claim into an invariant.

**Process rules**: "before you change it, pin it" — prompt/guard changes get a scenario first; falsify each safety eval once (break the guard, watch it fail, restore). Document-extraction fixture PDFs include a declared-type mismatch case.

**Prior art**: greenfield — no existing tests; the approach above is the standard.

## Further Notes

- **LangGraph fallback trigger**: if ADK blocks progress by end of day 1, swap the orchestration layer; tools, prompts, DB, UI, and eval runner are deliberately framework-agnostic to keep the swap cheap. Honest cost accounting: **Tier 1 memory sits inside the framework boundary** — DatabaseSessionService is ADK's, so the swap rebuilds conversation persistence on LangGraph's checkpointer (conceptually equivalent, different tables and API). The windowing and authority-ranking rules are framework-independent and carry over unchanged.
- **Day-4 priority order**: deploy → demo video → (only if both done) MCP tool server wrapper as tie-breaker.
- **Post-hackathon, deliberately not built — "soft escalate" for a clinical question mid-run.** As pinned, the state table sends *both* safety verdicts to `escalated`, which is terminal for automation: a patient halfway through a booking who asks "what dose should I take?" loses that run to the review queue and has to start again. That is the behavior as specified and it ships that way, because the alternative needs a state the machine does not have. The idea, recorded so it is not rediscovered as a bug: a **clinical-advice** verdict (never an emergency one) could refuse and escalate *without* closing the run — the booking stays live, the clinical question goes to a human, and the patient carries on choosing a time. It would need a new edge (`escalated` is currently the only destination and it is terminal), a second escalation-to-run relationship (one run, one open safety escalation, run still active), and a rule for what happens if the patient confirms a booking while a clinical question about them is unanswered. All three are real design work, none of it is scored, and the conservative behavior — hand the whole thing to a person — is the safe direction to be wrong in. Cost of the current behavior is one re-ask; cost of getting the new edge wrong is a live booking flow running alongside an unreviewed clinical question.
- **Open questions (deliberately unresolved, low stakes)**:
  - Exact Groq/OpenAI model choices (decide at build time; per-provider env vars make it a one-line change).
  - Hosting pick between Render and Railway for FastAPI.
  - Final department list and doctor counts are defaults, adjustable at seed time.
  - Demo video script/content.
  - ~~Whether the LLM safety classifier runs on every message or only on messages passing certain heuristics (cost/latency tuning at build time).~~ **Decided in Phase 5**: it runs on every message the deterministic screen passes, except one — a message the exact-token confirmation reader can read outright ("yes", "no"). Those are the two most common inputs the system receives and neither can be a subtle emergency, so a model call on them is a cost with no possible finding. The skip is recorded as a guard verdict rather than silently absent, because "the screen passed" and "the screen did not run" have to stay different facts.
- **Working principles of this build**: "the model proposes; the code disposes" (deterministic code owns every consequential decision), "the mock replaces the brain, not the hands" (only the LLM is simulated; tools, state, and persistence stay real), "redact at the pen, not the archive" (write-time redaction, never post-hoc), and "before you change it, pin it" (behavior changes get an eval scenario first).
- **Boundedness invariant (state in the README's design section)**: every table automation writes to has a growth rule, and every loop has an exit. Concretely — workflow runs (one active per patient; supersede), escalations (one open per run; triggers attach), missing-docs tasks (one open per appointment; upsert), reminders (attempt cap + idempotent delivery), agent turns (tool-iteration cap + one re-plan), confirmation re-asks (non-answer cap → templated yes/no). Any new automated writer or loop added later must declare its growth rule and exit before it ships.
- **Derivation invariant (the boundedness invariant's sibling, same README section)**: every row automation derives from another row has an update rule for when the source changes, applied in the source's transaction. Concretely — reminders follow their appointment (cancel → cancelled, reschedule → retimed), missing-docs tasks follow their appointment's document set (upsert/close), the visit-completion sweep follows the appointment's end time. Any new derived row added later must declare who updates it when its source moves.
- **Trace-completeness invariant (the third invariant, same README section)**: every turn is bracketed (one inbound event, one outbound event with its author), every LLM request is paired (exactly one terminal partner: response or error), every rejection is recorded (validation and guard verdicts, including passes). Enforced mechanically by the well-formedness checker in the wiring tests.
- Key decisions are also mirrored in the assistant's persistent project memory for continuity across build sessions.
